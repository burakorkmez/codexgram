# Privacy investigation — Codexgram

Reviewed 12 September 2026. This is a source audit of the testing application, not a certification of a deployed service. Read this inventory before the policy. The owner has confirmed testing purposes and requested placeholders. The application source matches the earlier terms audit snapshot; this review additionally examines installed authentication dependencies and native declarations. See `source-manifest.json` and `privacy-source-manifest.json` for reproducible hashes. References are repository-relative, with inclusive line ranges; vendor references require the inspected installed versions.

## Scope and method

Reviewed the Expo routes, components, contexts and hooks; Convex schema and every application function, HTTP route, authentication, storage and scheduled cleanup; configuration, dependencies, seed/demo code, tests, native iOS declarations and the static legal site. The earlier [repository inventory](INVESTIGATION.md) supplies the full feature/backend map. Traced identity → profile → upload → member visibility, and message → inbox → deletion. Examined installed Clerk token storage and telemetry instead of interpreting absence of an app analytics import as absence of SDK collection.

No credentials, private databases, production dashboards, live user traffic, provider contracts, backup contents or developer log contents were inspected. No real account was deleted. No compiled release or merged Android permission report was inspected. Provider defaults and declarations are distinguished from verified app behavior below. Negative findings mean no implementation was found in this source snapshot, not that an operator or vendor cannot perform the activity outside it.

## SDK telemetry, tracking and local storage

There is no direct app integration for advertising, cross-app tracking, analytics, crash reporting, payment data, push tokens, contact import, GPS or AI inference in the reviewed runtime source/dependency usage. This is a bounded negative finding, not a promise that vendors collect no diagnostics. Explore categories are regex-based, not AI profiling. Development tools and `.jolli` are not imported by the app runtime; their own developer telemetry is outside this user-policy scope.

Clerk SDK telemetry is a material exception to a blanket “no tracking” claim. The app does not pass a telemetry opt-out to ClerkProvider ([root](../src/app/_layout.tsx#L46), 46–49); EAS uses a development instance. The reachable [shared telemetry export](../node_modules/@clerk/shared/dist/telemetry.js#L1), 1–6, uses the inspected [collector chunk](../node_modules/@clerk/shared/dist/_chunks/telemetry-DZp9OI1j.js#L206). Its event path defaults to enabled for development instances, subject to environment/configuration, sampling and automation checks (206–251, 300–309). Payloads include SDK/Clerk versions, instance publishable identifier and event-specific data (395–406). POST destinations are `clerk-telemetry.com/v1/event` and `/v1/logs` (198–204, 332–355). There is no app user-facing opt-out control.

The same collector contains a separate log path with SDK versions, severity, message, timestamp, instance identifier and sanitized context (261–299). Its log gate returns true (303–305), unlike the development-only event gate. This establishes a dependency capability, **not proof that a specific log is emitted during this app's flow**. Actual calling paths, payloads and production behavior require a controlled native/web traffic review. Do not infer message/photo content is sent to Clerk telemetry, or claim all collection stops with the development-event switch. Clerk's [telemetry documentation](https://clerk.com/docs/guides/how-clerk-works/security/clerk-telemetry) describes development SDK usage telemetry and an operator opt-out; reconcile the installed log path with the vendor before making stronger claims.

The collector can use browser localStorage for event throttling, with memory fallback (same chunk, 119–150, 229–230). Native Clerk tokens use Expo SecureStore with `AFTER_FIRST_UNLOCK`: [token cache](../node_modules/@clerk/expo/dist/token-cache/index.js#L11), 11–35, 51. This is not a per-access biometric gate or a guarantee that uninstall erases credentials. Web does not receive that native cache. Browser SSO and web Clerk session/cookie behavior require an actual browser storage inventory; do not advertise a cookie-free authentication flow. Optional full Clerk resource caching is gated on an experimental option not supplied by this app: [singleton](../node_modules/@clerk/expo/dist/provider/singleton/createClerkInstance.js#L84), 84–157.

## Safeguards and their limits

- Identity-derived profile lookup and deletion locks: [auth helpers](../convex/lib/auth.ts#L4), 4–15; Clerk JWT issuer/audience configuration above. Owner checks for mutation/deletion and participant checks for messaging are implemented. These are source findings, not a penetration-test certification.
- Upload bearer authentication, ownership, MIME/byte/size checks and duration validation: [HTTP](../convex/http.ts#L9), 9–48; [uploads](../convex/uploads.ts#L7), 7–25. Validation is not malware scanning, moderation or metadata sanitization.
- Authenticated media retrieval uses `Cache-Control: private, no-store`; image clients disable their configured image cache: [HTTP](../convex/http.ts#L50), 50–71; [media](../src/components/social/media.tsx#L28), 28–53. OS/browser memory, screenshots and recipient copies are outside this guarantee.
- EAS service URLs are HTTPS. Native ATS disables arbitrary loads but permits local networking: [Info.plist](../ios/codexgram/Info.plist#L53), 53–69. Do not extrapolate universal transport configuration from one test build.
- Convex [describes encryption at rest](https://www.convex.dev/can-do/encryption), while backend functions can read decrypted data. App message storage has no client-side encryption layer. Avoid “only you and the recipient can ever read messages,” “zero knowledge,” or claims of the app's own security certification.
- No code evidence establishes operator access restrictions, access reviews, incident response, vendor retention, disaster recovery or deletion from backups. Those require operational evidence.

## User controls, permissions and release discrepancies

Implemented: edit profile, replace avatar, delete own posts/comments, manage follows/likes/bookmarks, sign out, delete account with retry handling, OS camera/photo permission choice. See the functions above and [profile UI](../src/components/social/profile.tsx#L62), 62–81. Device permission withdrawal affects future access, not already uploaded content.

Not implemented: data export/download, privacy request portal, private profiles, blocking, notification preferences, consent/cookie manager, user telemetry preference, age/DOB checks or a published in-app policy. Settings Privacy/Blocked/Notifications/Support/Report/Terms/Privacy Policy actions are alerts: [settings](../src/components/settings-screen.tsx#L36), 36–49. Sign-in policy/terms links are alerts, not accessible notices or versioned consent records: [entry](../src/app/index.tsx#L22), 22–24, 131–143. Missing UI does **not** remove statutory privacy rights; an actual staffed request channel is needed if applicable.

[app.json](../app.json#L48), 48–60 declares camera/photo permission text and disables microphone permission. [iOS Info.plist](../ios/codexgram/Info.plist#L64), 64–71 additionally contains Face ID and development local-network strings. A Face ID usage string alone does not establish collection of biometric templates by Codexgram. The reviewed token cache does not request biometric authentication. [PrivacyInfo.xcprivacy](../ios/codexgram/PrivacyInfo.xcprivacy#L5), 5–35 lists required-reason APIs but has empty collected-data types and tracking=false. **An empty declaration does not override actual personal-data collection.** Reconcile native manifests, merged dependency declarations and store disclosures for the actual distributed build. No equivalent final Android artifact was verified.
