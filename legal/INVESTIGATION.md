# Codexgram: term-relevant repository investigation

Reviewed 12 September 2026. Source baseline: `6975fa6e64d9034dbfd625591034ed456d8ce809`; file hashes and line counts are in [source-manifest.json](source-manifest.json). This is a source audit with local tests, not verification of a production deployment, provider dashboard settings, or actual retention in backups. No credentials were inspected and no real account was deleted.

## Method and evidence standard

Traced production routes through client state, validators, public functions, internal workers and storage; compared preview routes, screenshots and documentation; inspected the schema, dependency/build configuration, external calls and all backend function modules. Searched runtime source for payments, subscriptions, AI SDKs, rate limiting, moderation, eligibility, telemetry and legal acceptance. Ran the existing backend suite: **28 tests in 5 files passed**. Tests mock identities and Clerk HTTP; they do not certify live OAuth, infrastructure or legal enforceability.

References below give repository-relative file paths and exact line spans in the reviewed snapshot. A negative finding means no implementation was found in this scope, not that an external provider cannot impose a restriction. Contracts, permissions and liability allocations are proposed legal decisions; source code cannot establish that users already agreed to them.

## 6. Removal, account termination and retained data

Users can delete their own posts, stories and comments. Post removal deletes the post/media and asynchronously removes associated likes/comments/bookmarks/comment-likes, including others' interactions. A post owner cannot independently delete another person's comment. Avatar replacement deletes the old uploaded file. Evidence: [posts.ts](../convex/posts.ts), lines 45–64; [social.ts](../convex/social.ts), lines 60–67; [stories.ts](../convex/stories.ts), lines 35–47; [uploads.ts](../convex/uploads.ts), lines 41–48.

Settings → Delete Account confirms irreversible deletion, including both participants' conversations ([settings-screen.tsx](../src/components/settings-screen.tsx), lines 25–34). The request is derived from authenticated identity, requires a configured Clerk secret, marks `deletionRequested` and schedules workers ([accounts.ts](../convex/accounts.ts), lines 15–27). Normal use is gated during deletion, including failed jobs ([social-context.tsx](../src/context/social-context.tsx), lines 17–24, 42–51; [auth.ts](../convex/lib/auth.ts), lines 9–15). This flag is not an implemented abuse-suspension system.

Clerk identity deletion happens **before** app cleanup. Network/429/server errors retry; other failures preserve app data and offer retry. Cleanup proceeds after app closure/sign-out, in batches, without a guaranteed completion deadline ([accounts.ts](../convex/accounts.ts), lines 30–54, 58–131). Until cleanup removes records, other members may still see posts/profiles: reads do not uniformly filter authors' deletion flags ([posts.ts](../convex/posts.ts), lines 8–26; [profiles.ts](../convex/profiles.ts), lines 36–45; [views.ts](../convex/lib/views.ts), lines 11–30).

Cleanup removes owned posts/stories/media/avatar/uploads, comments/likes/bookmarks/comment-likes, follows, profile, and **entire conversations/messages/inbox entries for both participants**, including the other person's messages; unrelated accounts/content survive ([accounts.ts](../convex/accounts.ts), lines 59–115). It deletes the Codexgram Clerk identity, not the underlying Google or Apple account. Uninstalling or signing out does not request this deletion.

An `accountDeletions` record remains: token identifier, profile ID, state, attempts, optional next-attempt timestamp, plus system ID/creation time. Clerk user ID and error are cleared on success, but the retained identifier is not anonymous. No purge deadline, backup-erasure schedule, export tool, legal-hold workflow, deactivation/reactivation or cancellation of accepted deletion exists in source ([schema.ts](../convex/schema.ts), line 6; [accounts.ts](../convex/accounts.ts), lines 22–23, 47, 116–117; [profiles.ts](../convex/profiles.ts), line 21). Do not promise “all data immediately and permanently erased.”

No administrator suspension, moderation, appeals or provider-user-deleted webhook was found. Manual dashboard powers and their operational/legal process cannot be inferred as implemented product features. Draft reserves no invented discretionary ban system; proposed operator enforcement needs confirmation.

## 8. Backend map and complete exported surface

Profiles own posts/stories/uploads; posts own interactions; follows connect profiles. Conversations connect two profiles; messages belong to a conversation and sender; inbox rows belong to each participant. Account-deletion jobs reference a profile and auth identifier. Seed assets hold reusable seed source files. Indexes enforce access paths and relationship lookups; they are not themselves legal grants.

| posts | `list`, `get` queries; `publish`, `remove` mutations | `cleanup` mutation |
| social | `connections`, `comments` queries; `setLike`, `setFollow`, `addComment`, `deleteComment` mutations | — |
| postInteractions | `isBookmarked` query; `setBookmark`, `setCommentLike` mutations | `cleanupComment` mutation |

The cited modules above are the evidence for this surface. There is no `convex/crons.ts`; expiry/deletion use per-event scheduling.

Example flows: picker → client validation → `uploads.begin` → authenticated `/upload` byte/type/duration checks → `uploads.finish` → `posts.publish` → live feed query. Deletion confirmation → `accounts.requestDeletion` → Clerk DELETE → `identityResult` → batched `cleanup` → retained deletion marker.
